## Referential/model limitations detected
- `access_grants` has no `payment_id`/FK to `payments`; provenance cannot be verified per-grant.
- No FK constraints between `payments.user_id`/`access_grants.user_id` and `users.user_id`.
- `payments.tx_signature` appears constrained both by table-level unique and extra unique index (redundant but not harmful).

## Schema/timestamp observations
- `payments.created_at` null count: 0
- `access_grants.created_at` null count: 0
- Timestamp defaults exist, but consistency policies (UTC normalization across modules) are not explicitly enforced at DB level.

## Migration needs (recommended)
1. Add `payment_id` column to `access_grants` with FK to `payments(id)`.
2. Add unique constraint/index for active grant idempotency (e.g., `(user_id, feature_name, status)` filtered on active where supported).
3. Add FK constraints for user references where feasible.
4. Define canonical status enum and check constraints for `payments.status`.
5. Add auditing columns (`updated_at`, optional `granted_by`, `grant_reason`) for access lifecycle traceability.

## Risk summary
- **Critical:** none from direct DB corruption checks.
- **Medium:** grant/payment provenance gap due to missing relational link.
- **Medium:** existing active grants for users with no completed payment indicate historical drift or non-payment grant path.
- **Low:** index redundancy and enum/check-constraint hardening gaps.

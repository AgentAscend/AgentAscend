## Schema observations

### Payments
- `tx_signature` uniqueness present via table constraint + index.
- `amount` stored as `REAL` (floating precision risk for token accounting).

### Access grants
- No `payment_id` (or equivalent) foreign key to verified payments.
- No uniqueness guard for business-level entitlement linkage.

### Payment intents
- Table exists with `reference` PK, `expires_at_epoch`, `consumed_at`.
- No index on expiration fields (future cleanup performance consideration).

### Timestamps / migration needs
- `created_at` null checks for core tables returned 0 nulls.
- Timestamp formats are mixed style across code paths (`CURRENT_TIMESTAMP` SQL defaults vs ISO strings in some services); normalization policy would improve consistency.

## Migration recommendations
1. Add payment linkage to grants:
   - `access_grants.payment_id` (FK to `payments.id`) or equivalent immutable payment reference.
2. Add indexed integrity helpers:
   - index on `access_grants(user_id, feature_name, status)`
   - index on `payment_intents(expires_at_epoch)`
3. Consider decimal-safe storage strategy:
   - token amount as TEXT decimal or integer minor units.
4. Add periodic cleanup/repair jobs:
   - expired `payment_intents`
   - stale `idempotency_records` with null response older than threshold.

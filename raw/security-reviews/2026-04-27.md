# Security Review — 2026-04-27

## Scope
- Payments/auth/access: `backend/app/routes/payments.py`, `backend/app/services/idempotency.py`, `backend/app/services/access_service.py`, `backend/app/services/auth_service.py`
- Tools/Telegram: `backend/app/routes/tools.py`, `backend/app/routes/telegram.py`, `backend/app/providers/telegram_identity.py`
- Platform/marketplace/ops: `backend/app/routes/platform.py`, `backend/app/routes/marketplace.py`, `backend/app/routes/creator.py`
- Runtime/jobs: `backend/app/routes/jobs.py`, `backend/app/services/job_runner.py`
- App-level controls: CORS in `backend/app/main.py`
- DB constraints: `backend/app/db/session.py`
- Tests: `tests/test_payments_tools_security.py`, `tests/test_execution_ledger_endpoints.py`
- Repo secret exposure check + git state

## Executive Summary
Security posture is mixed: payment/idempotency/auth are materially improved, but there are **critical auth bypasses** on marketplace/platform ops endpoints that can grant access or modify ops data without authorization.

---

## Critical Findings

### C1 — Unauthorized marketplace entitlement grant
- Endpoint: `POST /marketplace/listings/{listing_id}/install` in `platform.py`
- Issue: No `Authorization` verification and no `require_user_access(payload.user_id, authorization)`.
- Impact: Any caller can install entitlements for arbitrary `user_id`.
- Class: Fake access grant / privilege abuse.
- Pre-public fix:
  1. Require auth header.
  2. Bind caller to `payload.user_id` via `require_user_access`.
  3. Add paid-listing payment verification gate before entitlement insert.
  4. Add regression test: unauthenticated and cross-user install must fail.

### C2 — Unauthorized marketplace status transitions
- Endpoint: `POST /marketplace/listings/{listing_id}/transition` in `marketplace.py`
- Issue: No auth enforcement; relies on payload actor values.
- Impact: Public caller can push listing lifecycle transitions.
- Class: Authorization bypass / workflow tampering.
- Pre-public fix:
  1. Require authenticated session.
  2. Require creator ownership or admin role.
  3. Ignore caller-provided `actor_user_id`; derive from session.

### C3 — Unauthenticated ops data exposure and mutation
- Endpoints in `platform.py`:
  - `GET /ops/audit-events`
  - `GET /ops/alerts`
  - `POST /ops/alerts`
  - `POST /ops/alerts/{alert_id}/ack`
  - `GET /ops/observability/dashboard`
- Issue: No auth/admin guard.
- Impact: Public read of internal telemetry/audit + unauthorized alert creation/ack.
- Class: Sensitive operational data leakage + control-plane abuse.
- Pre-public fix:
  1. Add `require_admin_session` to all `/ops/*` routes.
  2. Add rate limits and audit on all write ops.

### C4 — Telegram user spoofing risk
- Endpoint: `POST /telegram/command`
- Issue: Accepts raw `telegram_user_id` and maps to `tg:{id}` without Telegram signature/webhook verification.
- Impact: Caller can impersonate Telegram user IDs.
- Class: Identity spoofing.
- Pre-public fix:
  1. Verify Telegram webhook secret header / signed init data.
  2. Reject unsigned command payloads.

## Medium Findings

### M1 — Payment verification does not bind payer wallet to user identity
- `payments.verify` validates receiver and amount, but does not prove sender wallet ownership is bound to platform user session/wallet record.
- Risk: Shared signature or third-party payment ambiguity in some flows.
- Fix: require wallet challenge/sign-in and bind user↔wallet; verify tx source against bound wallet when required.

### M2 — In-memory rate limiting only
- `rate_limit.py` uses process-local memory buckets.
- Risk: resets on restart; ineffective across multiple instances.
- Fix: Redis/DB-backed distributed limiter for auth/payment/ops sensitive routes.

### M3 — Unstructured historical artifacts can include env/command traces
- Secret scan found conversation JSON/history files containing command arguments and variable names.
- Risk: accidental sensitive leakage in repo artifacts.
- Fix: add pre-commit + CI secret scanner, and redact/archive policy for conversation artifacts.

### M4 — CORS regex is environment-driven with wildcard method/header
- `allow_methods=["*"]`, `allow_headers=["*"]`; regex may be over-broad if misconfigured.
- Fix: pin strict origin list and tightly scoped methods/headers in production.

### M5 — Idempotency lock semantics can return 409 during in-flight collisions
- Correct but operationally noisy under concurrency bursts.
- Fix: add retry/backoff guidance and consistent client handling.

---

## Low Findings

### L1 — Dependency manifest minimalism / drift risk
- Only 4 top-level requirements; transitive versions not pinned.
- Fix: add locked constraints per environment.

### L2 — Logging hygiene mostly safe, but harden further
- Current logs avoid obvious secrets in reviewed routes.
- Fix: central sensitive-key scrubber for logs/errors.

### L3 — Runtime policy enforcement is partly procedural
- Policies exist but enforcement centralization is limited.
- Fix: single enforced policy gate for shell/file ops in runtime executor.

---

## Payment/Replay/Fake Access Specific Assessment
- Replay protection: **present** (`tx_signature UNIQUE`, idempotency records).
- Payment intent reference binding: **present** (`payment_intents` with expiry/consume).
- Access grant sequencing: **generally correct** (after payment insert).
- Major exception: **marketplace install bypass (C1)** allows fake access-like grants independent of payment.

---

## Pre-Public Fix Checklist (Must Complete Before Public Launch)
1. Lock down C1/C2/C3/C4 (critical) with tests.
2. Add admin guard middleware for all `/ops/*`.
3. Add Telegram signature verification.
4. Add distributed rate limiting.
5. Add wallet binding model for payment identity-sensitive flows.
6. Add CI secret scanning (block merges on high-confidence leaks).
7. Add security regression test suite for marketplace install/transition and ops endpoints.

## Overall Risk Rating
**Current: High (pre-public).**
Can move to **Medium** after critical auth bypasses and Telegram identity spoofing are fixed and tested.

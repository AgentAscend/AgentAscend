# Tokenized Agent Flow Review — 2026-04-27

## Current Reality (Codebase)
- Agent CRUD exists in platform routes (`/agents`, `/agents/{id}` etc.).
- Marketplace listing/install models exist.
- Payments currently gate at least one tool flow (`random_number`).
- No production-grade, explicit tokenized-agent issuance flow is implemented yet (manual strategy references exist in MEMORY/wiki/raw docs).
- No pump.fun integration code path was found in backend runtime routes/services.

## User Agent Creation Flow (Current)
1. Authenticated user can create agent record.
2. Ownership tracked via `owner_user_id` and/or audit fallback.
3. Agent lifecycle actions (start/pause/resume) exist.

## Manual vs Automatic Tokenization
### Manual (recommended MVP path)
- Keep tokenization off-chain/manual by ops team.
- Store metadata references only after verification.
- Avoid automatic token launch triggers.

### Automatic (future)
- Requires strict controls:
  - policy checks
  - allowlisted launch templates
  - budget limits
  - explicit human approval for every issuance

## Thresholds / Triggering
- Current code does not implement robust threshold-based tokenization triggers.
- Recommendation: do not auto-trigger tokenization based on installs/revenue until identity/payments/marketplace security is hardened.

## pump.fun Assumptions
- Strategy memory references pump.fun exploration, but backend integration is not observed.
- Any assumption that token launch is one-click in current product is incorrect.

## Payment Address Handling
- Payment routes rely on env-configured receiver wallet/mint.
- For tokenized-agent flows, segregate treasury/creator/revenue addresses and map by listing/agent ID.
- Add explicit address registry table and validation before settlement actions.

## Buyback/Burn Implications
- Keep as ledger/accounting concept first.
- Do not couple buyback/burn execution to user install or request path.
- Add governance and reconciled accounting before any execution automation.

## Marketplace Implications
- Paid listing install must require secure auth + verified payment.
- Entitlements should be grantable only through validated install/payment workflows.
- Current open install path must be fixed before any tokenized-agent monetization claims.

## MVP vs Future
### MVP
- Non-tokenized secure marketplace + payment-gated utility.
- Optional “tokenized roadmap” badges/metadata without financial execution logic.

### Future
- Wallet-bound creator issuance tools.
- On-chain entitlement receipts.
- Governed treasury automation and token utility policies.

## Recommended Next Steps
1. Close marketplace install/transition auth gaps.
2. Implement wallet binding and signed identity for creators/users.
3. Add explicit tokenization metadata schema (no auto-launch).
4. Build settlement ledger and reconciliation before token-finance features.

## Verdict
Tokenized-agent direction is strategically valid, but implementation should remain **manual + controlled** until core payment/access/marketplace security is fully hardened.
